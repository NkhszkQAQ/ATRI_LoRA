# QQ 机器人：RAG 与私聊长期记忆

这是现有 AstrBot + NapCat + ATRI 多模型网关的可选接入方式。它不重新训练，也不替换正在运行的 Qwen 模型进程。原聊天数据库继续由 AstrBot 管理，新增记忆使用另一份 SQLite；不要覆盖或迁移原聊天库。

## 用户怎么用

在 QQ **私聊**中，每条命令单独发送：

```text
/memory remember 喜欢的饮料=乌龙茶
/memory list
/memory forget 喜欢的饮料
/memory clear
```

保存后换个会话问“我喜欢喝什么？”。普通聊天不会自动保存；当前会话里的纠正不等于更新保存值。每位用户最多24条，名称64字符、内容400字符，其他容量边界沿用[长期记忆说明](LONG_TERM_MEMORY.md)。

群聊不读取私人记忆；保存、查看、删除命令会提示改用私聊。原来的聊天历史、群聊会话划分与白名单规则保持原配置。用户本身主动在群里发出的内容，仍按原有聊天规则处理。

## 接入结构

```text
QQ → NapCat → AstrBot（身份校验、私聊记忆插件）
                → 本机 RAG/记忆代理 → 原来的8B/4B模型服务
原模型切换插件 → 原模型网关（继续提供当前模型选择）
```

- 代理读取原网关的当前模型选择，并将每次请求固定到相应原后端；不启动另一份Qwen模型。
- 默认 `v1.1-8B` 接入 RAG 与事实检查；DT、4B保留原生成行为，同时可以使用私聊记忆。不将8B的实测范围扩展宣称为DT/4B的事实准确率。
- 插件从 AstrBot 的已验证平台事件获取平台ID与QQ发送者ID，不能用消息正文或请求体的 `user` 字段选择记忆归属。
- 插件仅将当前私聊用户的记录放入带时效的 HMAC 签名上下文。代理校验并移除传输标记，再进行检索、记忆参考或明确查询的直接回答。代理本身不开放记忆数据库管理API。
- 群聊签名上下文不含私人记录。签名无效或过期时拒绝，未验证入口不能读取私人记忆。签名用于完整性验证，不是加密；两端应同机运行并仅监听loopback，私钥及数据库须保存在受限目录。
- 多问题、重答、来源回退与受约束SSE沿用[v1.3流程](V1_3.md)。部分事实回答会偏书面，有限规则仍可能漏掉新错误。

### 私聊的活跃上下文

代理只向模型发送最近 **8 个历史用户轮次及当前轮次**；一个轮次包含其全部助手回复、工具调用和结果，不拆开工具链。间隔达到 **6 小时**时建立新的短期话题边界，后续请求及代理重启后继续遵守该边界。群聊和没有 QQ 签名的入口维持原行为。

插件从 QQ 事件取得消息实际发送时间，从当前会话取得 ID 和最近更新时间，经原有签名一起传给代理；请求中的 `user` 字段不能指定会话归属。代理添加带日期、时区的当前时间和发送时间提示，并优先回应最新要求。旧版插件仍可使用轮数窗口，升级插件后才具备会话间隔信息。

这些操作只影响模型请求，**不更改 AstrBot 的完整历史、不自动提取或删除长期记忆**。超过活跃窗口的对话仍在 AstrBot 存档中，但本次改动不新增历史检索功能；需要跨会话使用的稳定偏好仍通过 `/memory` 明确保存。窗口和时间提示能减少串话，不能保证模型一定完成改写等指令。

可用 `context_window.max_history_turns`、`idle_timeout_seconds` 和 `timezone` 调整默认值（默认时区 `Asia/Tokyo`）；`max_history_turns=0` 只保留当前轮。`context_db` 存放私有的会话边界状态，默认是 `memory_db` 同目录下的 `qq-context.sqlite3`，不要指向聊天库或记忆库。它只存归属摘要、时间、历史指纹和边界偏移，不存聊天正文。保留此文件才能在重启后延续边界。

已有部署需要同时更新代理与插件中的 `atri_bridge.py`，再更新插件 `main.py`；新代理还需要同目录的 `atri_context.py`。保持 AstrBot 原有轮数限制不变，避免其裁剪结果覆盖存档。日志只记录选择前后的条数和是否出现时间边界。相关研究与限制见[上下文串话调查](QQ_CONTEXT_RESEARCH.md)。

## 部署准备

需要已经能正常回答的原模型服务和网关。代理环境安装[misc/requirements-rag.txt](../misc/requirements-rag.txt)、FastAPI、uvicorn、httpx，以及模型服务同版本兼容的Transformers/tokenizers。embedding与重排在CPU运行。建议独立venv并固定原训练栈版本，避免升级原环境。

1. 按[RAG说明](RAG.md)构建带事实元数据的v1.3索引。原作索引含原文，只保存在部署者机器，不提交Git。
2. 复制[integrations/astrbot/runtime.example.json](../integrations/astrbot/runtime.example.json)，填写原网关、各模型后端、索引、tokenizer、缓存与新记忆库路径。新记忆库路径应与旧聊天库不同。
3. 在权限700的数据目录生成至少32随机字节的签名密钥文件，权限600。配置也应只允许部署者读取，不把密钥填进源代码、命令行或Git。
4. 启动代理：`python tools/atri_qq_proxy.py --config /private/path/runtime.json`，默认只监听 `127.0.0.1:9013`。先验证 `/health` 与实际模型回答，再更改机器人入口。
5. 将 `integrations/astrbot/atri_rag_memory/` 放入 AstrBot 的插件目录，同时把 `tools/atri_bridge.py`、`tools/atri_memory.py` 复制到该插件目录。将 `settings.example.json` 复制为私有 `settings.json`，只填写 `config_path` 指向运行配置；不要把该设置文件提交Git。
6. 备份 AstrBot 配置、启动脚本和聊天数据库。WAL模式数据库应使用SQLite在线backup接口，不能只复制主文件。备份保留在受限目录，不上传原聊天或密钥。
7. 短暂停止AstrBot后安装插件，将对应provider的 `api_base` 切到代理 `/v1` 并重启。原模型网关、切换插件、模型进程及NapCat可以保持运行。不要在入口仍指向旧模型时提前加载签名插件，否则旧模型看不到代理的剥离步骤。

启动顺序为模型/原网关 → RAG代理就绪 → AstrBot。若原脚本在SSH登录时自动执行，必须同时检查“已有服务正在加载”的进程状态，不能仅因健康接口尚未出现就再启动一个模型；并发启动脚本需加锁。代理缺失时不要把带私人上下文的请求偷偷转发到其他后端。

## 验证与回滚

本次接入自动化测试涵盖签名篡改/过期、主体隔离、群聊不读写、明确命令才保存、旧历史/多模态内容保护、模型选择、JSON/SSE与长度限制。代替模型测试不能证明QQ实际收发。

2026-11-06在现用RTX3080Ti机器上，使用真实AstrBot `ProviderRequest`、插件导入及现有8B服务完成9项接入前检查，包括资料+记忆混合回答、双用户隔离、群聊保护、无依据设定、无效签名、真实HTTP/SSE和原模型后端保留。接入前使用隔离的虚构用户记忆库，没有向QQ联系人发送自动测试消息；另验证24条满容量中文记录经实际HTTP传输可用。

上线后完成了QQ账号扫码登录和反向WebSocket连接。用户在真实私聊中依次验证保存饮品、询问自己的饮品、询问上学动机，并确认三条均正常回复。服务器另确认示例偏好已落盘、真实QQ请求使用签名上下文、原3个会话标识仍保留。这与上述合成事件检查分别记录；没有据此宣称真实群聊、大量用户并发或全部问法均已验证。

回滚时停止AstrBot，将provider入口恢复为原地址，把新插件移出活动目录，关闭代理的自启标记，再启动原机器人。**保留新记忆数据库，不自动还原旧聊天数据库备份**，以免覆盖上线期间产生的新聊天。代理及索引可以保留到确认回滚成功后再处理。

配置、索引、模型缓存和新记忆库会持续占磁盘；CPU检索及检查可能增加几秒延迟。重启机器人会短暂中断回复。上述服务检查、QQ实际收发、模型训练、PR合并及发布是独立状态，应分别报告。
