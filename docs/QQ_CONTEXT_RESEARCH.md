# QQ 跨时间话题串入：调查与修复

调查日期：2026-11-06。

## 公开报告与现成方案

1. [AstrBot #10859](https://github.com/AstrBotDevs/AstrBot/issues/10859)：用户报告缺少日期、使用处理时间而非消息发送时间，会让机器人混淆今天与昨晚。其案例是群聊积压，与本次私聊并非完全相同。截至调查时 issue 仍为 Open，关联了贡献者的时间戳补丁；不能据此宣称上游已发布完整修复。
2. [官方上下文压缩文档](https://docs.astrbot.app/use/context-compress.html)：`max_turns=-1` 仅表示不按轮数截断，不代表关闭 token 压缩。未知模型的窗口兜底值是 128000；未超过阈值时不会压缩。容量上限不等于话题相关性或时间边界。
3. [AstrBot #8972](https://github.com/AstrBotDevs/AstrBot/issues/8972)：报告请求裁剪后的工作上下文可能被用于覆盖完整存档。该 issue 关闭后转入 #9936 跟踪，关闭不代表修复已发布。本次不通过改写 AstrBot 历史来处理窗口。
4. [Social Context 插件](https://github.com/kazamisama/astrbot_plugin_social_context)：已有短期原文、较早摘要、TTL 的分层思路；主要用于群社交观察，附带主动判断等功能，不直接替代本项目私聊链路。此次采用时间分层和原始存档分离的思路，不引入该插件及其额外模型调用。

找到相关报告和可借鉴的实现思路，未找到可直接安装、同时满足现有私聊签名记忆、保留完整存档及模型切换约束的完整修复。

## 本机证据及判断边界

只读检查确认：同一私聊会话累计 92 条消息，跨日旧话题仍在原始历史内；轮数限制为 -1，当前日期提示关闭，历史消息只有角色与正文，没有逐条时间。长期记忆没有该旧话题。当前代码会读取完整会话，再交给代理与后端。

这证明链路缺少短期话题边界，是串话的直接风险。历史请求没有完整请求体快照，不能把当前代码重建当成当时请求的逐字记录；同时，模型没有真正换比喻属于另外一项生成质量问题，需单独验证。

## 本次实现

在代理内建立请求级窗口：默认保留 8 个完整历史用户轮次；实际发送时间间隔达到 6 小时后建立新边界。参数是本项目可调整的选择，不是上游推荐的固定数值。边界单独持久化，按已签名的用户及会话隔离；检测到历史重置或编辑时重新校验偏移。

剪裁在 RAG 检索、事实规划、JSON/SSE 和所有模型分流之前执行。签名携带实际消息发送时间和会话更新时间；新日期提示仅作用于请求。长期偏好仍由现有明确保存的记忆机制提供。工具链和多模态当前轮完整保留。

不训练或替换 LoRA，不自动总结私聊为长期记忆，不删除存档，不保证超出活跃窗口的旧闲聊可被自动召回。以后如需历史检索，应另行定义相关性及隐私边界。

## 验证标准

- 跨日旧调侃不进入当前改写请求，近期被要求改写的内容保留。
- 长间隔边界在后续消息与代理重启后保留；不同用户、会话及 reset/编辑相互隔离。
- 使用实际发送时间判断间隔，排队延迟不制造假断档，乱序消息不使时钟倒退。
- 签名时间字段拒绝异常值；匿名入口与群聊保持原行为。
- 工具调用和结果成组保留，JSON/SSE、模型切换和明确保存的长期记忆通过回归。
- 实际 GPU 对照测试与上述自动化测试分别报告；不向 QQ 联系人发送自动测试消息。

## 本轮验证结果

本地上下文/签名/代理测试通过；记忆及事实规划的无 Torch 用例另外通过 65 项。完整 RAG 测试在临时本地环境因缺少 llama-index 无法收集；依赖 Torch 的 8 项记忆/事实测试未在该本地环境执行。未为这些检查升级现有服务依赖。

3080 Ti 上使用 AstrBot 本身虚拟环境中的真实 `ProviderRequest`、`Conversation` 和修复插件，验证实际事件发送时间能够正确通过签名传输，原会话历史保持不变。

实际 GPU 对照采用只读的原会话前缀、现有 8B 服务及真实 CPU RAG；通过隔离的临时代理运行，没有向 QQ 发送消息。种子 11、22、33 三组中，修复后均给出了新比喻，模型请求都不含旧用户句子；每次上游请求为系统消息、8 个历史轮次及当前用户消息，共 18 条，输入 token 从 2928 降到 1870（约减少 36%）。

检查期间另一个语气修复版本已经切入现用入口。为保护该项工作，隔离候选在该版本上仅叠加本次上下文变更，保留其语气代码和索引。当前旧链路的三次回放也没有复现“煽情”原句，所以这轮不能证明生成质量改善完全由本次窗口修复造成。可直接确认的是旧历史在输入侧被隔离、近期改写对象保留及新旧修复兼容。

上述为部署前的代码和隔离链路验证，不代表所有闲聊质量问题都已解决。
