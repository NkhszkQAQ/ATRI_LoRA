# 主动 RAG 与回答安排：第一轮

隔离运行时可显式开启 `--rag-planning`，或在私有 JSON 配置中设置 `"rag_planning": true`，默认关闭。新增检索后的信息检查、最多两轮额外补查和带来源的回答安排。角色首次回答原样保留，训练、模型替换及部署另行决定。

当前状态：真实模型仍未达到采用门槛。Colab 已复现旧规划器错误；检索需求拆分与逐项证据检查是新的修复候选，程序检查通过，真实模型复验待完成。历史 Windows 实测及新候选的边界见后文。

## 调用与权限

首次 `plan` 保留既有记忆处理。实验开启时，新增一次独立 `lookup_plan`：只列当前问题需要核实的角色资料与最多两个查询，不再让记忆的 quotation/temporary 等分类决定角色检索。原话与近期用户上下文仍参与首次检索。之后 `review` 对每项资料需求核对实际来源或明确缺口，并提出补查。每轮最多两个查询，最多两轮额外补查，**首次检索批次不计入这两轮**。重复规范化查询、没有新增准入资料、检索失败或两轮用尽后停止；允许再做一次信息检查形成最终交接，但不会继续检索。

`lookup_plan`、`review` 使用同一底座并关闭角色 LoRA，`answer` 使用原 LoRA。可选规划 schema 仍只作用于首次 `plan`，不会将记忆提取格式错套到另两种调用。所有首次原始文本与校验结果均保留；格式、需求覆盖或来源校验失败时保留缺口，不通过重答修复规划或角色首答。

实验开启时，plan、lookup_plan 与 review 都收到程序固定的 `answer_actor`（亚托莉，assistant），明确用户直接称呼的“你”和委托对象；引用/转述仍按原对话解析。该字段不是实际用户或记忆所有者，不由请求或模型选择。补齐身份信息不等于模型已能正确理解请求或取得原作事实。

补查只调用原来的 `StageCorpus.search`，沿用启动时的原作 SHA/场景范围校验、阶段内检索、既有重排阈值、跨查询合并排序与上下文预算。当前原话的可选 dense 补充权限不扩展到模型查询。服务阶段、身份、查询次数和预算不由模型或请求 body 决定。

自定义 search 回调属于受信程序边界，须满足与 StageCorpus 相同的来源核验合同；运行时不接受缺少证据的裸片段。模型不能提供回调或通过 JSON 自建来源。完整资料与交接共用原有 7000 字符预算，先为完整交接保留空间，再裁去排名靠后的整条资料；不截断已选事实。模型调用仍受原有 token 预算约束。

## 两层交接

`answer_plan` 由程序生成。lookup_plan 声明资料需求，程序分配 n1 等本轮 ID；review 为每项需求提交 checks（need_id、source_ids、gap）。程序拒绝遗漏需求、重复需求 ID、资料外来源或“无来源且无缺口”，将所有支持来源自动绑定为 must_respond。事实、出处、边界与操作结果由程序复制。

| 字段 | 含义与约束 |
| --- | --- |
| `must_respond` | 必须回应，每项含 source_id、完整 fact 与实际 evidence。只能选择送入 review 的资料，不接受模型自拟事实摘要。 |
| `optional_reference` | 相同的来源绑定格式，按需使用。未选择的预算内资料仍可作为普通 references。 |
| `fact_boundaries` | 按来源 ID 绑定完整命题。主体、否定、程度由完整事实保留，并附阶段、事件时间、揭示时间、知识状态。 |
| `information_gaps` | 仍未知、冲突及失败/停止提示；未命中不等于不存在。 |
| `operation_results` | 从实际执行 trace 复制并去除随机数据库 ID，不接受模型提供的成功状态。 |

v2 另附 information_needs、coverage、story_stage、stop_reason。review 不再输出 status/must_respond；程序从逐项核对与查询推导状态。仍有缺口却没有补查词时记录 planner_no_query，不能当作资料齐全；检索需求格式失败记录 invalid_lookup_plan。来源是否真的支持需求、需求是否完整仍是模型的语义判断，ID 合法不证明这些已正确。角色提示要求自然回应，不朗读字段或查询过程；JSON/SSE 返回相同的首次角色回答，内部查询只在私有 trace 中保存。

本轮只新增 RAG 补查。既有记忆选择与操作位置保留，在补查之前仅执行一次；review 无写入/更正/删除入口。MEM 补查及完整操作失败验收属于下一阶段，不能因交接已有操作结果就宣称这些能力已通过。

## 验收与复现

程序测试覆盖两轮上限、重复查询、无新结果、首次/补充检索失败、来源 ID 伪造、阶段过滤、完整事实与共享预算、记忆操作不因补查重做、失败写入结果及 JSON/SSE 隔离。修复前的验证记录：596 passed、1 skipped、6 subtests passed；跳过项为当时未安装的可选规划格式库，保留 6 条既有依赖弃用警告。新候选另补逐项覆盖、空证据、漏查与诊断隔离测试，结果单独报告。

使用旧日志的首次规划、旧角色首答及当前真实 CPU StageCorpus，完成 6 条旧题和 7 条预先封存表达变体的程序重放。学校、家务、未知接口及四种剧情阶段均覆盖，13/13 程序合同通过。学校与家务在补查后取得相应事实；未知接口未取得型号，停止并保留未知；剧情资料按阶段提供。未修改阈值、原作卡片、人设或角色权重。

**重放的 review 决策为明确标记的测试夹具，并非新模型输出。** 它证明给定查询/选择时程序能否执行正确，不证明模型会自主产生这些查询。旧角色首答只是不同旧输入下的历史证据，不是新输入下的 LoRA 验收结果。该阶段按用户选择未启动 GPU；随后单独进行了下述真实模型批次，不能用夹具重放的13/13代替真实结果。PR 保持 Draft。

`tools/eval_answer_planning.py` 支持互斥的 replay / real 模式。replay 显式传入历史目录、lookup 夹具和新 checks 格式的 review 夹具，记录来源哈希、实际命中、模型输入、回答安排、历史首答及虚构用户库前后状态。旧的 status/must_respond 格式不会自动当作新证据核对结果。real 模式拒绝历史目录与所有夹具，要求 `--execute`、底座 manifest、适配器 SHA 和显式本地路径；在空闲 GPU 核对加载身份后保存所有新鲜首次输出。评估器不读取最终留出集。

```sh
python tools/eval_answer_planning.py --mode replay \
  --cases /private/evaluation/cases.jsonl \
  --lookup-fixtures /private/evaluation/lookup-fixtures.json \
  --review-fixtures /private/evaluation/review-fixtures.json \
  --historical-dir /private/evaluation/old-results \
  --script-source /private/script-source \
  --reranker /private/models/frozen-reranker \
  --out /private/evaluation/new-replay
```

正式采用前需真实模型全链路复验：分别判断第二层的自主查询、补查、核心事实安排，以及第一层的完整回应、事实边界、未知表达和角色语气。网页 JWT 与 Colab 尚未增加实验开关；共享 Runtime、隔离 HTTP/QQ 构造器可显式启用，不表示真实 QQ 通讯或各平台验收通过。

## Colab 复现与规划器修复候选（2026-11-09）

用户的 Colab L4 完成学校、家务两道题的4次旧规划器请求，八个底座/tokenizer文件、输入token和显式生成参数均核对一致；3次首次输出逐字相同。未加载LoRA也复现学校不查且空资料判足够、家务补查泛化为做菜教程。它定位到规划环节，尚不能单独断言是提示词、8B能力、思考模式或量化中的哪一项原因。

新候选拆出单一职责 lookup_plan，并把“足够”的自报改为逐项证据检查。角色权重、人设、卡片、重排阈值、NF4/计算精度、采样、两轮补查上限均保留。开启实验后每条消息多一次512 token上限的底座调用；尚未测得其真实时延与语义通过率。

`tools/eval_planner_only.py` 可以在已有 Colab 底座上运行同一 Runtime、StageCorpus 和生成器；必须显式使用 base_only 诊断路径，不接受已加载的LoRA，也不允许生成角色回答。Runtime 的 generate_answer=False 仅用于程序控制的诊断，HTTP body 无法开启它；trace 的 final 为 null，并标明角色生成未运行，不用替身文本冒充首答。源码包独立导入，避免 notebook 缓存了旧规划器。

验收沿用原6题并封存7条新表达。程序重放使用显式 lookup/checks 夹具，与真实模型结果分别存档。Colab 续测先核对底座、重排模型SHA与原6题CPU重排分数，再让模型实际提出查询和检查资料；新依赖与平台差异保留记录，不降低0.5准入阈值。角色语气及LoRA事实能力不在本次单独验收范围，完整链路仍须后续复验。功能默认关闭，PR继续Draft，不训练、不部署。

本候选全套程序检查为631 passed、6 subtests passed，保留6条既有弃用警告。使用当前真实CPU检索与明确标记的lookup/checks夹具，13/13程序重放通过；这些不是模型自主规划成绩。另在Mac隔离的torch2.7.1、transformers4.57.1、sentence-transformers3.4.1环境核对原6题重排，最大分数差约2.1e-7、0.5阈值准入结果全部相同；此项是CPU依赖兼容检查，不能当作Colab GPU或规划语义验收。
